# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local pipeline that generates long-form Vietnamese drama stories via a local Ollama LLM (or, optionally, the DeepSeek cloud API — see Config below), then optionally converts the finished story to voice-over audio via a local Python TTS worker (VieNeu-TTS with voice cloning). By default everything runs locally against `localhost:11434` (Ollama) and a local Python environment; DeepSeek is an opt-in alternative for the story-generation LLM calls only.

## Commands

- `npm install` — install deps (tsx, typescript; no test framework, no linter configured)
- `npm run dev -- .\stories\example\idea.txt` — run the story pipeline on an idea file, writes to `output/<idea-filename>/`
- `npm run tts -- .\output\<idea-name>` — build a TTS manifest from a generated story and run the Python worker to synthesize audio (requires a Python env with `vieneu` installed and a voice sample)
- `npm start` — launch the local web UI (Express + SSE) on `http://localhost:4000` (override with `PORT`); drives story generation and TTS through the browser instead of the CLI

There are no test or lint scripts. `tsc` is a dependency but not wired to a script; use `npx tsc --noEmit` to type-check if needed.

`npx tsx scripts/smoke-prompts.ts` runs only the Story Bible → Outline → Hook stages against `stories/example/idea.txt` and prints the craft fields plus a chapter-range check, writing to `output/_smoke/`. Use it to iterate on `src/prompts.ts` without paying for a full story run.

## Architecture

### Story generation pipeline (`src/index.ts` → `src/pipeline.ts`)

`generateStory(config, idea, outDir, onProgress?, shouldAbort?)` runs a fixed sequence of LLM calls, each stage caching its output to disk under `outDir` so a rerun resumes instead of regenerating. `onProgress` (optional) receives `ProgressEvent`s (`bible`/`outline`/`chapter`/`scene`/`edit`/`error`/`stopped`/`complete`, see `src/types.ts`) as each stage starts/caches/completes; `shouldAbort` (optional) is polled between steps and, if it returns true, aborts the run by throwing `Error("ABORTED")`. Both are used by `src/server.ts` to drive the web UI's live progress and stop button; the CLI (`src/index.ts`) calls `generateStory` without them.

Before stage 1, `appendRunInfo` **appends** an entry to `run-info.json` (provider, resolved model, chapter/scene/duration settings, temperature, plus `numCtx` for Ollama only). It appends rather than overwrites because a story can legitimately be produced by more than one model — chapters 1–3 on Ollama, the rest resumed on DeepSeek — so a single `model` field would misreport it. This is the only record of which model wrote a story; nothing else on disk carries it, and `settings.json` is git-ignored and overwritten in place. Stories generated before this existed cannot be recovered.

1. **Story Bible** (`story_bible.json`) — title/genre/theme/premise/tone/characters/setting/conflicts/ending plus the craft fields `moral` (one-sentence thesis), `motif` (a concrete recurring prop and the chapter where its meaning inverts), `antagonistWound` (the antagonist's root wound and its reveal chapter), `escalationLadder` (8–12 concrete physical beats, each using a *different* mechanism) and `titleCandidates`, from the `ARCH` prompt. `moral`/`motif`/`escalationLadder` are validated as required; `antagonistWound`/`titleCandidates` are asked for but not enforced. `ARCH` also receives `{{CHAPTERS}}` so every `*Chapter` field it emits lands inside the real chapter range. Five further craft fields come from the retention playbook (see `docs/playbook-ke-chuyen.md`): `coldOpen` (the disaster scene told *before* chapter 1, plus the jump-back line — reveals the catastrophe but never the mechanism behind it), `tellDetail` (a prop with a verifiable state, e.g. a knot tied a particular way, that silently reports tampering), `secondPredator` (the operator who cons the antagonist, so the villain is a victim before the law arrives), `truthWitness` (a child or neighbour whose offhand truth gets dismissed and echoes back at the decisive moment), and `ledger` (5–8 concrete numbers anchoring the whole story). None are enforced by validation.
2. **Outline** (`outline.json`) — N chapters (`config.chapters`) via the `OUT` prompt, validated by `validateOutline`. Each chapter additionally carries `povCharacter` (≥2 chapters must be seen from the antagonist's eyes), `escalationType` (unique per chapter, drawn from `escalationLadder`), a strictly increasing `pressureLevel`, `protagonistAction` (what the protagonist actively *does* that chapter), `dramaticIrony` (what the audience knows this chapter that the protagonist does not — required per chapter and never repeated) and `antagonistInsert` (a 150–300-word cut-away to the antagonist working in secret; `SC` makes exactly one scene per chapter carry it, from the antagonist's POV). `cliffhanger` must now be a physical event or a line of dialogue, never a rhetorical question. `validateOutline` only enforces `chapter`/`title` — the rest is prompt-level, deliberately, to keep retries cheap on weak local models.
3. **Hook** (`hook.txt`) — the ~260-word spoken intro ("lời dẫn") via the `HOOK` prompt: proverb + subversion → the `coldOpen` disaster staged as a scene with a line of dialogue → what has already been lost → motif image → dramatic question → the `timeJump` jump-back line → "Mời quý vị cùng lắng nghe." Cached like every other stage.
4. Per chapter, per scene (`config.scenesPerChapter`):
   - **Scene plan** via `SC` prompt, validated by `validateScenePlan`. Scenes also carry `povCharacter`, `pronounRegister` (`anh-em` / `tôi-cô` / `mày-tao` — the Vietnamese pronoun pair is the relationship thermometer), `signatureProp` (a named Vietnamese everyday object) and `newIncident` (one new physical event), the last two required to be unique within the chapter.
   - **Scene draft** via `WR` prompt (`retryLLM`, not JSON — raw story text), appended to a running chapter draft. Last 6000 chars of the draft are passed back in as `RECENT` context for continuity, and `USED` carries `usedEmotionalBeats`/`usedEscalationTypes` from memory as an explicit do-not-repeat list.
   - **Memory update** via `MEM` prompt after each scene — tracks `characterState`, `knownFacts`, `revealedSecrets`, `unresolvedQuestions`, `foreshadowing`, `lastChapterSummary`, plus `usedEmotionalBeats` (anti-repetition), `usedEscalationTypes` (stops the same escalation mechanism being reused), `motifOccurrences` and `timeline` (ages/elapsed time, so later scenes don't contradict earlier ones). Memory failures are logged and swallowed (non-critical); story-critical stages are not.
   - After all scenes: **chapter edit pass** via `EDIT` prompt, cleaned, and written to `chapter-<n>.txt`. Chapter files are the resume checkpoint — if `chapter-<n>.txt` already exists, the whole chapter (planning/writing/editing) is skipped.
5. **Outro** (`outro.txt`) — the ~450-word spoken closer via the `OUTRO` prompt: final image → what stays open → a discussion question about a *grey* secondary character → restated `moral` with a fresh motif metaphor → comment CTA.
6. `hook.txt` + all chapter files + `outro.txt` are concatenated into `final_story.txt`.
7. **Continuity check** via the `CHECK` prompt over the assembled story, written to `continuity-report.json` (timeline contradictions, dropped threads, repeated emotional beats, flat characters, duplicated escalation mechanisms). Non-critical like `MEM` — a failure is warned about and the run still completes.
8. **Craft review** written to `review-report.json`, cached like every other stage (the file existing skips the whole stage). Lives in the exported `reviewStory(c,out,onProgress?,shouldAbort?,force?)` so the web UI can run it on demand; `generateStory` calls it at the end only when `config.autoReview` is on. One `REVIEW_CH` call *per chapter* — reading `chapter-<n>.txt` against its outline entry and scoring `hook`/`nhipDo`/`showKhongTell`/`hoiThoai`/`cangThang`/`nhanVat` 0–10 with quoted evidence per issue — then one `REVIEW_SUM` call scoring the whole story (`cauTruc`/`vongCungNhanVat`/`caoTrao`/`ketThuc`/`doMoiLa`/`bamMoralMotif`) and merging repeated chapter issues into `topIssues`. It is per-chapter rather than one pass over `final_story.txt` because `CHECK`'s `slice(0,60000)` already drops the climax and ending on a full-length story. Report-only: it never rewrites the story. Non-critical at two levels — a single chapter that fails after retries is recorded as `{chapter,error}` and the loop continues, and the whole stage is wrapped so any other failure only warns (`ABORTED` is re-thrown so the web UI's stop button still works). `REVIEW_SUM` is told the real chapter count via `{{TOTAL}}` so a story missing a few chapter scores to review errors isn't judged as unfinished.
9. **Fix pass** — exported as `fixStory(c,out,onProgress?,shouldAbort?,force?)`, run at the end of `generateStory` only when `config.autoFix` is on (default off), cached by `fix-report.json`. Reads `review-report.json` and rewrites the chapters that `needsFix` selects: any chapter with a `severity:"cao"` issue, or with any score ≤5. Each one goes through `FIXCH` (that chapter's review issues are handed back as the edit instructions, with the plot/names/ages/timeline explicitly frozen), then **`FIXVERIFY` checks each targeted issue against the rewritten text one by one** and `REVIEW_CH` re-scores it. The rewrite is kept when at least one targeted issue is verified gone; it is reverted only when no issue was fixed, or when the score total collapsed below 85% of the original. The score is a floor against a botched rewrite, not the deciding vote — a fix that removes a wrong pronoun or a broken timeline earns its place even if the numbers stay flat, because consistency is what the reader actually feels. `FIXVERIFY` also reports `newProblems` (contradictions, lost plot, mangled sentences the edit introduced); those are surfaced in the report and on the review screen rather than triggering an automatic revert, since `pre-fix/` always holds the original and the call is the user's. The pre-fix text is always kept at `pre-fix/chapter-<n>.txt`; a rewrite shorter than 85% of the original is rejected outright. `final_story.txt` is rebuilt only if at least one fix was kept. `fix-report.json` records `{chapter, kept, note, issuesTargeted, issuesFixed, newProblems, scoresBefore, scoresAfter}` per chapter, so a reverted fix still says why. `POST /api/fix/:name` also takes `{maxRounds}` (1-10, default 1), surfaced as the **Số vòng sửa tối đa** field. Above 1, `fixStory` loops: after each round the chapters it kept already carry fresh `REVIEW_CH` scores *and a fresh issue list* from the verify step, so those are written straight back into `review-report.json` and become the next round's input — no separate review pass, no extra call. Round 1 targets what `needsFix` (or the hand-picked selection) says; later rounds target every chapter still carrying a `cao` or `vừa` issue, and hand `FIXCH` only those issues. The loop stops at whichever comes first: nothing left above `thấp`, the round cap, or a round where no rewrite was kept (the model has stopped making progress and further rounds only cost calls). When more than one round ran, `REVIEW_SUM` is re-run once at the end so the overall score and `topIssues` describe the story that now exists. `fix-report.json` records the `round` on every entry plus the total `rounds`.

The report is written *before* `final_story.txt` is rebuilt: the rebuild is the step most likely to fail (a half-written story has no file for every outline chapter, which is why it is now skipped rather than throwing), and losing the report of a rewrite that already happened on disk is worse than skipping the rebuild. Note `pre-fix/` is a subdirectory rather than `chapter-<n>.orig.txt` because `src/tts/index.ts`'s fallback globs `chapter-*.txt` and would otherwise splice the stale copies into the audio.

Prompts (`src/prompts.ts`) are Vietnamese and instruct the model to output either strict JSON (no Markdown) or plain narration text (no Markdown, no meta-commentary like "Dưới đây là..."). `cleanGeneratedStory` (`src/utils.ts`) strips Markdown artifacts and stock LLM preambles from narrative output as a second line of defense.

### Retry/validation model (`src/ollama.ts`)

Two retry wrappers around `askLLM`, both doing 3 attempts. `askJSON` steps temperature down each retry (`t` → `0.2` → `0.1`) to trade creativity for format compliance, since its failure mode is malformed JSON. `retryLLM` deliberately does **not** — it retries at the configured temperature, because its failure modes (network/API errors, empty response, `max_tokens` truncation) are not caused by temperature, and collapsing a long-form narrative generation toward greedy decoding invites degenerate repetition, making the retry likelier to fail than the first attempt. Both sleep between attempts (`backoffMs`): exponential with jitter from an 800 ms base, or a 5 s base when the error text looks like throttling (`429`/`529`/`503`/"rate limit"/"overloaded") — without this, parallel jobs burn all 3 attempts within a second of a single rate-limit response.

- `askJSON` — expects JSON, uses `extractJSON` to strip code fences / find the outermost `{}`/`[]` if the model wraps the JSON in prose, then runs an optional `validate(x)` callback that throws on missing/malformed fields.
- `retryLLM` — expects non-empty raw text (used for scene writing and chapter editing).

Per the README: Story Bible, Outline, Hook, Chapter Plan, Scene Writing, Chapter Editing and Outro are all critical — if they still fail after 3 attempts, the whole run aborts (no partial/corrupt story is written). Memory updates and the continuity check are the non-critical stages that retry but don't abort the run on failure.

### TTS pipeline (`src/tts/index.ts` + `src/tts/worker.py`)

Runs after a story exists, either manually via the CLI or driven by the web server:

1. The exported `runTTS(storyDir, opts, onProgress?)` reads `final_story.txt` (or falls back to concatenating `chapter-*.txt`), cleans Markdown, splits into ≤450-char segments on paragraph/sentence boundaries, and writes `tts/manifest.json` (segments with id/text/output path).
2. It spawns `python src/tts/worker.py --manifest ... --voice ... --ref-audio ...`, which loads `vieneu.Vieneu`, does reference-audio voice cloning per segment, and writes `tts/audio/<0001>.wav` etc. Existing output files >1000 bytes are skipped, so reruns resume like the story pipeline.
3. Default voice sample path is `voices/minhthu.mp3`; override with `TTS_REF_AUDIO`. `TTS_REF_TEXT` (transcript of the sample) improves cloning quality when set.
4. `opts.pipeOutput` controls stdio: unset/falsy (the CLI path, `main()` at the bottom of the file) uses `stdio: "inherit"` so the Python process's TTY/prompts pass through untouched; `pipeOutput: true` (used by `src/server.ts`) pipes stdout/stderr instead, parsing `[i/total] SKIP|TTS ...` lines out of stdout into `TtsProgressEvent`s (`src/types.ts`) for `onProgress`.

### Web server (`src/server.ts`)

Express app (`npm start`, default port 4000, binds `127.0.0.1` only) serving `public/` statically and `output/` at `/output` for direct file access (story text, audio).

**Generate jobs run many-at-a-time.** In-memory state is a `Map<name, GenerateJob>` (`generateJobs`) plus a FIFO `jobQueue`; `pump()` promotes queued jobs to running while `runningCount() < maxParallelStories`, and is re-run whenever a job finishes, a job is stopped, a batch is submitted, or the limit changes via `POST /api/settings`. Job identity is the story name, so each job writes to its own `output/<name>/` and they never collide; re-submitting a name that is already `queued`/`running` 409s. `POST /api/generate` accepts either one story (`{name, idea|ideaFile, ...}`) or a batch (`{items: [...], ...shared config}`) and returns the queued names plus per-item `failed` entries — a bad item never blocks the rest. `POST /api/generate/stop` takes `{name}` (a queued job is dropped from the queue and marked `stopped` immediately; a running one gets `abortRequested`) or `{all: true}`. Per-story SSE stays at `GET /api/generate/stream?name=`, replaying buffered events on (re)connect and now including scheduler events `queued`/`started`; `GET /api/jobs` and `GET /api/jobs/stream` expose a whole-queue snapshot (`JobSummary[]`, `running`, `maxParallelStories`) that drives the home screen's queue panel.

Parallelism is deliberately **across** stories, not within one — scenes depend on the previous scene's `RECENT` text and chapters on the running memory, so intra-story concurrency would break continuity. Because each job's LLM calls are strictly sequential, concurrent LLM requests equal running jobs, which is why one knob (`maxParallelStories`) is enough.

TTS is still single-job-at-a-time (`ttsJob`): `POST /api/tts/:name` 409s if one is running, since the Python worker is GPU/CPU-bound and parallelising it would not help. All routes that resolve a filesystem path from request input go through a shared `resolveUnder(root, name)` helper to keep the path inside `output/`/`stories/`.

### Config (`src/config.ts`, `src/types.ts`)

All tunables live in one `Config` object, overridable via env vars: `OLLAMA_MODEL`, `OLLAMA_URL`, `OLLAMA_NUM_CTX`, `PYTHON_COMMAND`, `TTS_VOICE`, `DEEPSEEK_API_KEY`, `DEEPSEEK_MODEL`, `MAX_PARALLEL_STORIES` (`src/tts/index.ts` imports `config` for the TTS ones; it separately reads `TTS_REF_AUDIO`/`TTS_REF_TEXT` from env since those aren't in `Config`). Story length is controlled by `durationMinutes × targetWordsPerMinute`, chapter/scene count by `chapters`/`scenesPerChapter`.

`Config.numCtx` (Ollama only, default 32768) is **one budget shared by prompt and generation**, not a prompt-only limit — Ollama stops with `done_reason:"length"` the moment `prompt_eval_count + eval_count` reaches it, which surfaces downstream as a truncated reply: `Invalid JSON` from `extractJSON` on the JSON stages, or a half-written chapter on the narrative ones. The old 4096 default sat right at the Outline stage's real cost (measured: 1647 prompt + ~2200 generation tokens), so runs failed intermittently depending on how verbose the model happened to be, and all 3 retries failed together because temperature does not change how much output the task needs. Lower it via `OLLAMA_NUM_CTX` only if the GPU cannot hold the KV cache (9B at 32768 ≈ 6.2 GB VRAM).

`Config.maxParallelStories` (default 3, clamped to 1–16 when set from `settings.json`) caps how many generate jobs the web server runs at once; it is a server-only knob (the CLI runs one story per process). Set it to 1 for Ollama, higher for DeepSeek/Claude.

`Config.editorModel` (default empty, `EDITOR_MODEL` or the Settings dropdown) swaps the model used by stages 8 and 9 only — `generateStory` derives an `ec` config from `c` with the model fields replaced, and every review/fix call takes `ec` while everything that writes the story takes `c`. Provider is deliberately not overridable: the point is "write with the cheap model, judge with the strong one", and a model grading its own prose is the failure this exists to avoid (a run where Haiku wrote chapters 6-12 was only caught because the review happened to run under a stronger model). It is recorded in `run-info.json` when set.

`Config.autoReview` / `Config.autoFix` (both default off; `AUTO_REVIEW=1`/`AUTO_FIX=1` or the Settings checkboxes turn them on) gate stages 8 and 9 at the end of `generateStory`. They default off because both stages cost N+1 and 2-per-chapter extra LLM calls and the fix stage overwrites chapter files, so the normal flow is: write the story, read the report, then decide.

Stages 8 and 9 are also reachable on demand via `POST /api/review/:name` and `POST /api/fix/:name`, driven by the **Chấm điểm** / **Sửa N chương có lỗi** buttons on a story's screen. Those routes call `reviewStory`/`fixStory` with `force=true` — a button press must actually re-run, so the file-existence cache only serves the automatic path. They are queued as ordinary jobs (`GenerateJob.kind` is `"generate" | "review" | "fix"`), which is why the queue panel, SSE stream, stop button and `maxParallelStories` cap all work on them without a second job mechanism. `/api/fix/:name` 400s when there is no `review-report.json` yet, and `reviewStory` scores only the chapters that exist on disk so the button is safe to press on a half-written story.

Both routes accept an optional `{provider, model}` body so a single review or fix run can go to a different backend than the one in `settings.json` — cross-checking a DeepSeek-written story with Claude, or re-scoring with a stronger model just this once. The override applies to that job only and never writes `settings.json`. An explicit choice clears `editorModel` for that run, because `editorModel` is a bare model name that belongs to the configured provider and would be meaningless once the provider changes. `review-report.json` and `fix-report.json` therefore record `provider`/`model`: with the judge now selectable per run, a score is not interpretable without knowing who gave it.

`POST /api/fix/:name` also accepts `{selection: {"<chapter>": [issueIndex, ...]}}`, produced by ticking individual issues on the review screen. With a selection present `fixStory` ignores the `needsFix` filter and rewrites exactly the listed chapters, handing `FIXCH` only the ticked issues — so a chapter can be fixed for one specific complaint without the model rewriting around the other five. `fix-report.json` records `issuesTargeted` per chapter. Everything else (the `pre-fix/` backup, the 85% length floor, the re-score-and-revert guard) applies unchanged.

`/api/stories` and `/api/stories/:name` report `staleChapters`: chapters whose `chapter-<n>.txt` mtime is newer than the score that applies to them, i.e. rewritten since they were last judged. The reference time is `review-report.generatedAt`, except for a chapter the fix stage rewrote *and kept* — that text was re-scored inside the fix stage, so its reference is `fix-report.generatedAt` and it must not be flagged. The UI marks those rows "cũ" and warns on the story screen and the home table, because a score displayed next to text it was not computed from is worse than no score at all.

`Config.provider` (`"ollama"|"deepseek"`) selects which LLM backend `src/ollama.ts`'s `askLLM` calls — Ollama's `/api/chat` or DeepSeek's OpenAI-compatible `/chat/completions`, both behind the same `askJSON`/`retryLLM` retry wrappers, so nothing downstream of `askLLM` needs to know which provider is active. `loadSettingsOverrides()` (`src/config.ts`) reads an optional `settings.json` (git-ignored, repo root) and returns override fields; both the CLI (`src/index.ts`) and the web server (`src/server.ts`, `POST /api/generate`) merge it over the base `config` before each run, so switching provider via the web UI's Settings screen (`GET`/`POST /api/settings`) takes effect for the CLI too without restarting anything. Absent `settings.json` behaves exactly as before (`provider:"ollama"`). Once a user saves the Settings screen, `settings.json` becomes the source of truth for `model`/`provider`/`deepseek` and outranks the env-var defaults (e.g. `OLLAMA_MODEL`) from that point on.

## Code style note

Source files under `src/` (excluding `src/tts/index.ts`) are written densely — no whitespace between statements, minimal formatting. This appears to be the existing convention for the core pipeline files; match it when editing those files rather than reformatting.
