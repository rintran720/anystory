# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local pipeline that generates long-form Vietnamese stories — family drama or doting romance, in a Vietnamese or Chinese setting, see **Genre and setting** below — via a local Ollama LLM (or, optionally, the DeepSeek cloud API — see Config below), then optionally converts the finished story to voice-over audio via a local Python TTS worker (VieNeu-TTS with voice cloning). By default everything runs locally against `localhost:11434` (Ollama) and a local Python environment; DeepSeek is an opt-in alternative for the story-generation LLM calls only.

## Commands

- `npm install` — install deps (tsx, typescript; no test framework, no linter configured)
- `npm run dev -- .\stories\example\idea.txt` — run the story pipeline on an idea file, writes to `output/<idea-filename>/`
- `npm run tts -- .\output\<idea-name>` — build a TTS manifest from a generated story and run the Python worker to synthesize audio (requires a Python env with `vieneu` installed and a voice sample)
- `npm start` — launch the local web UI (Express + SSE) on `http://localhost:4000` (override with `PORT`); drives story generation and TTS through the browser instead of the CLI

There are no test or lint scripts. `tsc` is a dependency but not wired to a script; use `npx tsc --noEmit` to type-check if needed.

`npx tsx scripts/smoke-prompts.ts [drama|ngontinh]` runs only the Story Bible → Outline → Hook stages of that genre against its example idea (`stories/example/idea.txt` or `stories/example-ngontinh/idea.txt`, default `drama`) and prints the craft fields plus a chapter-range check, writing to `output/_smoke-<genre>/`. Use it to iterate on `src/prompts/` without paying for a full story run.

`npx tsx scripts/snapshot-prompts.ts <genre>` re-renders every prompt of that genre into `scripts/__snapshots__/` (plus `settings.txt`); `npx tsx scripts/check-genre-prompts.ts` asserts the cross-genre invariants. Both are offline and free. Run them, plus `git diff --exit-code scripts/__snapshots__/`, after any change under `src/prompts/` — see **Genre and setting** below.

## Architecture

### Genre and setting (`src/prompts/`)

Two independent axes decide what a run writes. **Genre** (`Config.genre`, `"drama" | "ngontinh"`) picks the prompt set — the craft the story is made of. **Setting** (`Config.setting`, `"vietnam" | "china" | "auto"`) picks the world those prompts are dressed in — names, everyday props, proverbs, currency, bureaucracy. They are two axes rather than one because the doting-romance spine is not inherently Chinese and the family drama is not inherently Vietnamese; each genre only declares a `defaultSetting` (`drama` → `vietnam`, `ngontinh` → `china`) that `"auto"` resolves to, and either genre can be run in either world.

`src/prompts/` is four kinds of file:

- **`core.ts`** — the genre-neutral half: `P()` (the `{{VAR}}` substituter), the `GenrePrompts` interface, and the shared craft text with the `build*` functions that assemble it (`buildWR`, `buildSC`, `buildMEM`, `buildEDIT`, `buildFIXCH`, `buildFIXVERIFY`, `buildREVIEW_CH`, `buildREVIEW_SUM`, `buildCHECK`, `buildHOOKFIX`). What lives here is what is true of *any* voice-over story: `WR_RULES.cauNganChoGiongDoc` (short sentences — the listener cannot rewind), `WR_RULES.conSoCuThe`, `EDIT_TASKS.xoaLapY`, the frozen-plot clause in `FIXCH`, the 0–10 grading scale, the JSON-only tails, `NO_META`.
- **one spine per genre** — `drama.ts`, `ngontinh.ts`. The spine owns everything the genre *is*: the Story Bible fields `ARCH` asks for, and the subset of them `bibleRequired` enforces (drama asks for `escalationLadder`/`coldOpen`/`antagonistWound`/`tellDetail` but enforces only `escalationLadder` of the four; romance asks for and enforces all of `sweetLadder`/`doubtLadder`/`heroineWound`/`maleLeadSecret`/`happyEnding`); the Outline fields (`escalationType`/`pressureLevel`/`antagonistInsert` versus `sweetBeat`/`doubtBeat`/`intimacyLevel`/`swoonLine`/`maleLeadInsert`); the scene fields and which pronoun registers exist at all (`mày-tao` is offered by drama's `SC` and forbidden in romance); which core `WR_RULES` it composes and which rules are its alone (drama's `CÂU BÁO TRƯỚC:`/`DƯ LUẬN:`, romance's `NGÔI KỂ:`/`NỘI TÂM TỰ TRÀO:`/`CÂU THOẠI SÁT THƯƠNG:`/`KHÔNG BẠO LỰC:`); the Hook/Outro formula and its `hookWords`/`outroWords` (drama 260/450, its hook closing on the channel's fixed line "Mời quý vị cùng lắng nghe" and its outro opening on "Quý thính giả thân mến"; romance 70/150 and neither of those two fixed lines — its outro is still channel voice, just its own); `actsText(chapters)`; `chapterCriteria`, the six `REVIEW_CH` score keys; and `usedMemoryKeys`, the anti-repetition lists `MEM` maintains — romance *replaces* rather than extends drama's pair here: drama tracks `usedEmotionalBeats`/`usedEscalationTypes`, romance tracks `usedEmotionalBeats`/`usedSweetBeats`/`usedDoubtBeats`/`usedSwoonLines`, four keys and no `usedEscalationTypes` (it has no escalation ladder to repeat). Every key any spine lists here also needs a cap in `MEMORY_CAPS` (`src/utils.ts`) or that list grows without limit and is pasted whole into every later prompt; `check-genre-prompts.ts` asserts the two agree. Stages 1–9 below describe the drama spine; the romance spine substitutes its own fields at every one of them.
- **`settings.ts`** — `SETTINGS` (one `SettingPack` per setting) plus `settingVars(id)`, which expands a pack into six variables. Five land in exactly one prompt each: `{{SET_NAMES}}` in `ARCH`, `{{SET_PROP}}` in `SC`, `{{SET_DETAIL}}` in `WR`, `{{SET_PROVERB}}` in `HOOK`, `{{SET_FOREIGN}}` in `FIXCH`. The sixth, `{{SET_JUDGE}}`, is the only one that appears in more than one — it goes into all three judging prompts (`REVIEW_CH`, `REVIEW_SUM`, `CHECK`), because a judge that does not know which world it is reading falls back on the one word it can see. Drama carries all six; **romance carries five** — its `HOOK` is forbidden to open on a proverb, so it deliberately has no `{{SET_PROVERB}}`. A spine must never hardcode a country — `check-genre-prompts.ts` asserts that no spine's `ARCH`/`SC`/`WR`/`FIXCH` contains the string "Việt Nam", because the moment one does, the other setting silently stops working; and, because that assertion is blind to the opposite sabotage, it also asserts that each slot above still holds its variable, that no prompt carries a `{{SET_*}}` the map does not put there or `settingVars` does not fill, and that no `SettingPack` field is empty.
- **`index.ts`** — `GENRES` (the dropdown list), `getGenre(id?)`, `resolveSetting(genre, setting)`, and the re-exports the rest of the codebase imports.

**`REVIEW_SUM`'s six keys are identical in every genre on purpose** — `cauTruc`, `vongCungNhanVat`, `caoTrao`, `ketThuc`, `doMoiLa`, `bamMoralMotif`. `REVIEW_CH` differs in exactly two of its six: the first four (`hook`, `nhipDo`, `showKhongTell`, `hoiThoai`) are shared craft, and only the last two carry the genre (drama `cangThang`/`nhanVat`, romance `ngotNgao`/`namChinh`). Freezing the summary keys means `needsFix`, `scoreSum`, `staleChapters` and the whole summary screen never have to know which genre they are looking at; only the per-chapter table is genre-aware, and it reads its column headers out of the report itself (`reportCriteriaKeys` in `public/app.js`) rather than from a hardcoded list, so a key nobody has a label for still renders as itself instead of `undefined`.

Genre and setting are stamped into `story_bible.json` as **`genreId`** and **`settingId`** the moment the bible is written, and `generateStory` then re-resolves its prompt set and setting variables from what the file now holds rather than from the job config. The write is `bible.genreId ?? c.genre`, so **an existing value always wins on resume**: a story cannot change identity halfway through because someone reran it with a different dropdown value, which would splice romance chapters into a drama. That `??` alone was not enough, because it only protects a bible that already carries a stamp: a story written before this branch has none, so a resume would have stamped whatever the form said onto it and re-resolved the spine from there — a romance rubric over a drama bible with no `sweetLadder`, for every remaining chapter and every later review and fix. So `queueGenerateJob` (`src/server.ts`) now resolves genre/setting from the story's own `story_bible.json` whenever that file exists and **ignores `input.genre`/`input.setting` entirely** — via `getGenre`/`resolveSetting`, so an unstamped bible resolves to the same `drama`/`vietnam` every reader of that file already assumes. `public/app.js` hides the two selects when the create form is opened with a prefilled name (its resume signal) and does not submit a hidden field, because a control that cannot change anything must not look like it can. The story screen prints the resolved `genre · setting` under the title (`#run-genre`, from the bible `/api/stories/:name` already returns), because the `Sửa N chương` button on that screen applies whichever `{{SET_FOREIGN}}` the bible names and nothing on the page used to say which. `reviewStory`/`fixStory` take no genre argument at all — they read `genreId`/`settingId` off the bible — so a story scored days later, from another machine or another provider, is still judged by the rubric it was written to. The field is `genreId` rather than `genre` because `ARCH` already emits a free-text `genre` ("ngôn tình hiện đại, hôn nhân hợp đồng") for its own use and a machine-read key must not collide with prose. A bible carrying neither field reads as `drama`/`vietnam`, which is exactly what every story generated before this existed is.

Genre resolution deliberately behaves differently in two places. `getGenre` and `resolveSetting` **fall back silently** — unknown, empty or missing means drama / the genre's default — because their callers are *reading stories already on disk*, where a missing value means an old file and refusing to render it helps nobody. `POST /api/generate` instead returns **400** on an unrecognised `genre` or `setting`, because there the value is a choice about work not yet done: silently writing a drama for someone who asked for a romance costs a full paid run. `POST /api/review|fix/:name` accepts `provider`/`model` overrides but **no** genre or setting override — the provider is a property of the judge, the genre is a property of the story that was already written. For the same reason `POST /api/generate` still 400s on an unrecognised genre for a *new* story but ignores the field outright once `story_bible.json` exists.

> **Warning — `{{SET_FOREIGN}}` is the one setting variable that can delete the cast.** It reaches a model through exactly one prompt: `FIXCH`, via `FIXCH_EXTRAS.tiengVietTuNhien` in `core.ts`, which is the only place the string `{{SET_FOREIGN}}` appears outside `settings.ts`. No `EDIT` prompt carries it, so the blast radius is the fix pass alone — which is also the only stage that overwrites finished chapters, and therefore the worst possible place for it to be wrong. Under `vietnam` it reads "xoá sạch từ nước ngoài, chữ Hán…". Under `china` it must invert to "**GIỮ NGUYÊN tên riêng Hán-Việt** của nhân vật, công ty và địa danh — đó là bối cảnh Trung Quốc, không phải lỗi dịch", and only then strip block Hán characters, English and Latin pinyin. Get this wrong — hardcode the Vietnamese wording, drop the variable out of `FIXCH_EXTRAS.tiengVietTuNhien`, or add a setting without writing its `foreign` clause — and the fix pass will dutifully "clean" Tần Dịch Thâm, Tô Duyệt and Lục Thiếu Khanh out of every chapter it rewrites. The failure is silent: chapter files are overwritten in place, the chapter can even score *higher* afterwards, and only `pre-fix/` still holds the cast. Any change to `SET_FOREIGN`, or to the prompts carrying it, has to be re-verified by actually running the fix pass on a Chinese-set story and diffing the name list before and after — no offline assertion can prove the model obeyed the inversion.

> **Warning — the judging layer used to be blind to the setting, and that is worse than it sounds.** `REVIEW_CH`, `REVIEW_SUM` and `CHECK` carried no `{{SET_*}}` variable at all, and both spines hardcoded *"thoại có tự nhiên như người Việt nói không"* into the `hoiThoai` criterion. On a Chinese-set story the judge read the words "tiếng Việt" in the intro, inferred Vietnamese people, and filed *"thoại thiếu tự nhiên so với tâm lý người Việt"* as a real defect. The damage does not stop at the report: `FIXCH` and `FIXSPAN` receive the review's issue list **as their edit instructions**, so the next fix pass is ordered to make Chinese characters behave like Vietnamese ones. Measured on `output/thu-ngontinh`: with the blind judge the story scored 7.5 with two `thấp` issues, both about Vietnamese manners; with `{{SET_JUDGE}}` in place the same text scored 5 and surfaced three `cao` issues the old lens never reached — a first-person POV that breaks to third mid-climax across all three chapters, a showdown that puts one character's lines in another's mouth, and a timeline where a character has already left at 8am while sitting in the study taking a call. The old 7.5 was not a good score; it was the wrong measurement. `check-genre-prompts.ts` now asserts that all three judging prompts carry `{{SET_JUDGE}}`, that none of them hardcodes "người Việt", and that china's `judge` clause is the *inverted* one that forbids docking points for un-Vietnamese behaviour.

**Adding a third genre:** write one spine file exporting a `GenrePrompts`, add its id to `GenreId` in `src/types.ts`, register it in `ALL` and `GENRES` in `index.ts`, add it to `asGenre` in `src/config.ts` — that function hardcodes the valid ids, so a genre it does not list is silently discarded when it arrives through `settings.json` or `STORY_GENRE`, and the run quietly writes a drama. If it introduces new `chapterCriteria` keys, add their labels to `CRITERIA_LABELS_SHORT`/`CRITERIA_LABELS_FULL` in `public/app.js`. Then four more places, none of which announce themselves:

- `public/app.js` — add the genre's name to `GENRE_LABELS`. Without it the story list falls back to showing the raw id (honest, but ugly); it used to fall back to drama's label, which quietly filed a third genre's stories under the wrong name.
- `scripts/check-genre-prompts.ts` — it hardcodes the expected id list (`GENRES … === "drama,ngontinh"`) and the per-genre `SET_SLOTS` map, so the safety net turns red on the first run until the new spine is listed in both. Add its own cross-contamination assertions while you are there; a spine nothing asserts against is a spine nothing protects.
- `scripts/smoke-prompts.ts` — it picks the idea file with a `genreId === "ngontinh" ? … : drama's file` ternary, so any third genre is silently smoke-tested against the *drama* idea and reads as if its own `ARCH` were broken. Add `stories/example-<id>/idea.txt` and a branch.
- `src/utils.ts` — `MEMORY_CAPS` holds the union of every genre's `usedMemoryKeys` with a per-key cap. A new genre's memory key that is missing there is never trimmed, so it grows every chapter and is pasted whole into every later prompt until the context budget goes. This is the one of the four that now fails loudly: `check-genre-prompts.ts` asserts `MEMORY_CAPS` covers every spine's `usedMemoryKeys`.

`src/pipeline.ts`, `src/server.ts` and `src/ollama.ts` need no changes — they read the spine through `getGenre` and never name a genre. That is the only part of this list that is safe to trust as complete: before believing you are done, run `grep -rn '"ngontinh"' src scripts public` and account for every hit.

**Adding a third setting:** add a `SettingPack` (all six fields, `foreign` included — see the warning above) to `settings.ts`, list it in `SETTINGS`/`SETTINGS_LIST`, add the id to `SettingId` in `src/types.ts` and to `asSetting` in `src/config.ts` (same silent-discard trap as `asGenre`), and add its label to `SETTING_LABELS` in `public/app.js`.

**Verifying prompt changes** — there is no test framework, so these three scripts are the whole safety net:

- `npx tsx scripts/check-genre-prompts.ts` asserts the invariants a refactor breaks quietly: that the spines have not bled into each other (romance's `ARCH` must not ask for `escalationLadder`; drama's `WR` must not carry the romance-only rules), that every key declared in `bibleRequired`/`usedMemoryKeys`/`chapterCriteria` is actually named in the prompt that has to produce it, that `WR` rule 2's by-number reference to its own exception rule still points at the rule it names (drama defers to “câu báo trước”, romance to “câu thoại sát thương”, and both happen to sit at rule 9), that `actsText(N)` cuts 1..N into three contiguous acts, that no spine hardcodes a country, that every `{{SET_*}}` variable is still in the one prompt that consumes it and nowhere else, that no `SettingPack` field is empty and that china's `foreign` clause is still the *inverted* one, and that `MEMORY_CAPS` in `src/utils.ts` caps every key the spines declare in `usedMemoryKeys`. It is written to go red on a *wrong* spine, not to praise a right one — the test for a new assertion is that the sabotage it exists to catch actually fails it: copying drama's `WR` onto the romance spine, writing the Vietnamese wording into romance's `FIXCH` in place of `{{SET_FOREIGN}}`, deleting `{{SET_PROP}}` from its `SC`, dropping a genre's memory key out of `MEMORY_CAPS`, or putting any `{{SET_*}}` into `HOOKFIX`.
- `npx tsx scripts/snapshot-prompts.ts <genre>` writes `scripts/__snapshots__/<genre>-prompts.txt`, `<genre>-meta.txt` and `settings.txt`; running it for both genres and then `git diff --exit-code scripts/__snapshots__/` is the only thing that catches a prompt whose text changed by accident during a refactor. Regenerate and commit the snapshots deliberately when a prompt change is intended.
- `npx tsx scripts/check-report.ts` asserts the `topIssues` chapter-number guard in `src/report.ts`, against the real 0-based sample that exposed it. Its heaviest assertion is a *negative* one: sanitising must **drop** an unreal chapter number, never shift the list by one to "repair" it. Adding 1 would be right most of the time, and that is exactly what makes it dangerous — when it is wrong it pins a confident wrong chapter on an issue and nobody can tell, whereas a missing number is visibly missing.
- `npx tsx scripts/check-spans.ts` asserts the paragraph locate/splice in `src/spans.ts`. Its heaviest assertion is that every character *outside* the replaced paragraphs survives a splice byte-for-byte — a splice bug is worse than no span mode at all, because it would touch what it promised not to touch while reporting "only one paragraph changed". It also pins the all-or-nothing location rule, the 12-character minimum anchor (a 4-word quote can match the wrong paragraph, and a wrong match means editing the wrong text), and right-to-left splicing (left-to-right shifts every later offset after the first replacement). Each of those three was verified to fail the script when deliberately broken.
- `npx tsx scripts/check-quality.ts` asserts the prose gate in `src/quality.ts` still rejects what it exists to reject. Its three fixtures are not invented: they are the same hook in three real states this pipeline produced — the generated original (26.7 words/sentence, one 36-word sentence), the choppy rewrite the first `HOOKFIX` draft caused (11.4 words/sentence, two sentences under 10 words), and the smooth one (16.2). Quality here is a **band, not a direction**: both failures sit outside it in opposite directions, which is exactly why fixing one used to cause the other. The load-bearing assertion is that the choppy version fails the gate when compared against the original — when that defect actually shipped, `tsc`, the snapshots and `check-genre-prompts.ts` were all green and only a human reading the text caught it.
- `npx tsx scripts/smoke-prompts.ts [drama|ngontinh]` runs only Bible → Outline → Hook against that genre's example idea (`stories/example/idea.txt` or `stories/example-ngontinh/idea.txt`), writing to `output/_smoke-<genre>/`, for cheap prompt iteration. It stamps `genreId`/`settingId` into the bible it writes exactly as `generateStory` does, so the cheap path exercises that contract too and the smoke output does not read back as a legacy drama. (`output/_smoke-ngontinh/` predates the stamp and still reads as one until it is regenerated.)

### Story generation pipeline (`src/index.ts` → `src/pipeline.ts`)

`generateStory(config, idea, outDir, onProgress?, shouldAbort?)` runs a fixed sequence of LLM calls, each stage caching its output to disk under `outDir` so a rerun resumes instead of regenerating. `onProgress` (optional) receives `ProgressEvent`s (`bible`/`outline`/`chapter`/`scene`/`edit`/`error`/`stopped`/`complete`, see `src/types.ts`) as each stage starts/caches/completes; `shouldAbort` (optional) is polled between steps and, if it returns true, aborts the run by throwing `Error("ABORTED")`. Both are used by `src/server.ts` to drive the web UI's live progress and stop button; the CLI (`src/index.ts`) calls `generateStory` without them.

Before stage 1, `appendRunInfo` **appends** an entry to `run-info.json` (provider, resolved model, chapter/scene/duration settings, temperature, plus `numCtx` for Ollama only). It appends rather than overwrites because a story can legitimately be produced by more than one model — chapters 1–3 on Ollama, the rest resumed on DeepSeek — so a single `model` field would misreport it. This is the only record of which model wrote a story; nothing else on disk carries it, and `settings.json` is git-ignored and overwritten in place. Stories generated before this existed cannot be recovered.

1. **Story Bible** (`story_bible.json`) — title/genre/theme/premise/tone/characters/setting/conflicts/ending plus the craft fields `moral` (one-sentence thesis), `motif` (a concrete recurring prop and the chapter where its meaning inverts), `antagonistWound` (the antagonist's root wound and its reveal chapter), `escalationLadder` (8–12 concrete physical beats, each using a *different* mechanism) and `titleCandidates`, from the `ARCH` prompt. `moral`/`motif`/`escalationLadder` are validated as required; `antagonistWound`/`titleCandidates` are asked for but not enforced. `ARCH` also receives `{{CHAPTERS}}` so every `*Chapter` field it emits lands inside the real chapter range. Five further craft fields come from the retention playbook (see `docs/playbook-ke-chuyen.md`): `coldOpen` (the disaster scene told *before* chapter 1, plus the jump-back line — reveals the catastrophe but never the mechanism behind it), `tellDetail` (a prop with a verifiable state, e.g. a knot tied a particular way, that silently reports tampering), `secondPredator` (the operator who cons the antagonist, so the villain is a victim before the law arrives), `truthWitness` (a child or neighbour whose offhand truth gets dismissed and echoes back at the decisive moment), and `ledger` (5–8 concrete numbers anchoring the whole story). None are enforced by validation.
2. **Outline** (`outline.json`) — N chapters (`config.chapters`) via the `OUT` prompt, validated by `validateOutline`. Each chapter additionally carries `povCharacter` (≥2 chapters must be seen from the antagonist's eyes), `escalationType` (unique per chapter, drawn from `escalationLadder`), a strictly increasing `pressureLevel`, `protagonistAction` (what the protagonist actively *does* that chapter), `dramaticIrony` (what the audience knows this chapter that the protagonist does not — required per chapter and never repeated) and `antagonistInsert` (a 150–300-word cut-away to the antagonist working in secret; `SC` makes exactly one scene per chapter carry it, from the antagonist's POV). `cliffhanger` must now be a physical event or a line of dialogue, never a rhetorical question. `validateOutline` only enforces `chapter`/`title` — the rest is prompt-level, deliberately, to keep retries cheap on weak local models.
3. **Hook** (`hook.txt`) — the ~260-word spoken intro ("lời dẫn") via the `HOOK` prompt: proverb + subversion → the `coldOpen` disaster staged as a scene with a line of dialogue → what has already been lost → motif image → dramatic question → the `timeJump` jump-back line → "Mời quý vị cùng lắng nghe." Cached like every other stage.
4. Per chapter, per scene (`config.scenesPerChapter`):
   - **Scene plan** via `SC` prompt, validated by `validateScenePlan`. Scenes also carry `povCharacter`, `pronounRegister` (`anh-em` / `tôi-cô` / `mày-tao` — the Vietnamese pronoun pair is the relationship thermometer), `signatureProp` (a named Vietnamese everyday object) and `newIncident` (one new physical event), the last two required to be unique within the chapter.
   - **Scene draft** via `WR` prompt (`retryLLM`, not JSON — raw story text), appended to a running chapter draft. Last 6000 chars of the draft are passed back in as `RECENT` context for continuity, and `USED` carries `usedEmotionalBeats`/`usedEscalationTypes` from memory as an explicit do-not-repeat list.
   - **Memory update** via `MEM` prompt after each scene — tracks `characterState`, `knownFacts`, `revealedSecrets`, `unresolvedQuestions`, `foreshadowing`, `lastChapterSummary`, plus `usedEmotionalBeats` (anti-repetition), `usedEscalationTypes` (stops the same escalation mechanism being reused), `motifOccurrences` and `timeline` (ages/elapsed time, so later scenes don't contradict earlier ones). Memory failures are logged and swallowed (non-critical); story-critical stages are not.
   - After all scenes: **chapter edit pass** via `EDIT` prompt, cleaned, and written to `chapter-<n>.txt`. Chapter files are the resume checkpoint — if `chapter-<n>.txt` already exists, the whole chapter (planning/writing/editing) is skipped.
5. **Outro** (`outro.txt`) — the ~450-word spoken closer via the `OUTRO` prompt: final image → what stays open → a discussion question about a *grey* secondary character → restated `moral` with a fresh motif metaphor → comment CTA.
6. `hook.txt` + all chapter files + `outro.txt` are concatenated into `final_story.txt`.
7. **Continuity check** via the `CHECK` prompt over the assembled story, written to `continuity-report.json` (timeline contradictions, dropped threads, repeated emotional beats, flat characters, duplicated escalation mechanisms). Non-critical like `MEM` — a failure is warned about and the run still completes.
8. **Craft review** written to `review-report.json`, cached like every other stage (the file existing skips the whole stage). Lives in the exported `reviewStory(c,out,onProgress?,shouldAbort?,force?)` so the web UI can run it on demand; `generateStory` calls it at the end only when `config.autoReview` is on. One `REVIEW_CH` call *per chapter* — reading `chapter-<n>.txt` against its outline entry and scoring `hook`/`nhipDo`/`showKhongTell`/`hoiThoai`/`cangThang`/`nhanVat` 0–10 with quoted evidence per issue — then one `REVIEW_SUM` call scoring the whole story (`cauTruc`/`vongCungNhanVat`/`caoTrao`/`ketThuc`/`doMoiLa`/`bamMoralMotif`) and merging repeated chapter issues into `topIssues`. It is per-chapter rather than one pass over `final_story.txt` because `CHECK`'s `slice(0,60000)` already drops the climax and ending on a full-length story. Report-only: it never rewrites the story. Non-critical at two levels — a single chapter that fails after retries is recorded as `{chapter,error}` and the loop continues, and the whole stage is wrapped so any other failure only warns (`ABORTED` is re-thrown so the web UI's stop button still works). `REVIEW_SUM`'s `topIssues[].chapters` is guarded in three places because one was not enough. The model sometimes emits **0-based array indices** instead of chapter numbers — the score table it receives is an array, so element 0 is chapter 1 — and the failure is silent: the JSON validates, the screen renders, the numbers just point at the wrong chapters. Observed on a three-chapter story: `chapters` came back `[0] [1] [2] [2] [2]` while the issue whose list said `[0]` had a detail reading "Cliffhanger ở chương 1", and the one saying `[2]` described the chapter-3 showdown. It is intermittent — the same prompt returned correct `[1,2,3]` on an earlier run — so the prompt fix alone cannot be trusted. (1) The JSON skeleton no longer shows `"chapters":[0]`, which was priming the zero, and the prompt now states the numbers must be the real `chapter` values in 1..`{{TOTAL}}`, never array positions. (2) `summarize` in `src/pipeline.ts` validates them against the chapters actually scored, so `askJSON` retries at a lower temperature; if the retry still fails it strips the unreal numbers rather than discarding the whole summary, because losing the overall score over one bad integer costs more than losing a few chapter labels. (3) `public/app.js` filters them again at render time, so **reports already written to disk display honestly without paying for a re-review**. Nothing anywhere adds 1 to "repair" a 0 — see `check-report.ts` for why.

`REVIEW_SUM` is told the real chapter count via `{{TOTAL}}` so a story missing a few chapter scores to review errors isn't judged as unfinished.
9. **Fix pass** — exported as `fixStory(c,out,onProgress?,shouldAbort?,force?)`, run at the end of `generateStory` only when `config.autoFix` is on (default off), cached by `fix-report.json`. Reads `review-report.json` and rewrites the chapters that `needsFix` selects: any chapter carrying a `cao` or `vừa` issue, or with any score ≤5. `needsFix` is deliberately the *only* selection predicate — it drives the button label, round 1, every later round and the loop's stop condition alike. An earlier version had round 1 select on `cao`-or-low-score while later rounds selected on `cao`-or-`vừa`, so a story whose chapters carried only `vừa` issues showed "Sửa 3 chương" and then quietly expanded to 12 on round 2. Each one goes through `FIXCH` (that chapter's review issues are handed back as the edit instructions, with the plot/names/ages/timeline explicitly frozen), then **`FIXVERIFY` checks each targeted issue against the rewritten text one by one** and `REVIEW_CH` re-scores it. The rewrite is kept when at least one targeted issue is verified gone; it is reverted only when no issue was fixed, or when the score total collapsed below 85% of the original. The score is a floor against a botched rewrite, not the deciding vote — a fix that removes a wrong pronoun or a broken timeline earns its place even if the numbers stay flat, because consistency is what the reader actually feels. `FIXVERIFY` also reports `newProblems` (contradictions, lost plot, mangled sentences the edit introduced); those are surfaced in the report and on the review screen rather than triggering an automatic revert, since `pre-fix/` always holds the original and the call is the user's. The pre-fix text is always kept at `pre-fix/chapter-<n>.txt`; a rewrite shorter than 85% of the original is rejected outright. A rewrite whose **prose measurably got worse** is rejected too, and that gate sits deliberately *before* `FIXVERIFY` and `REVIEW_CH`: a rewrite that already made the writing worse is not worth two more paid calls to adjudicate, so a chapter rejected on prose costs one call instead of three. The measurement is `compareProse` from `src/quality.ts`, whose count thresholds scale with passage length (`floor(sentences/25)`) — one new fragment in an 80-word hook is a defect, one in a 200-sentence chapter is noise, and blocking noise would revert good fixes.

**The fix pass rewrites paragraphs, not whole chapters, whenever it can.** `FIXCH` handed the model the entire chapter and asked it to fix three issues, which left it free to rewrite two thousand words to repair three sentences — that blast radius is the *source* of "fixing one thing breaks another", not a side risk. `rewriteChapter` (`src/pipeline.ts`) therefore tries `FIXSPAN` first. The anchors already exist and need no guessing: `REVIEW_CH` requires every `issue.detail` to quote real chapter text as evidence, so `locateIssues` (`src/spans.ts`) pulls the quoted span out of each detail and maps it to the paragraph containing it. The model receives the whole chapter with numbered paragraphs, the targets marked `<<<SỬA>>>`, and may return **only** those paragraphs as JSON — the blast radius is bounded at the *output*, not the input, so the untargeted text is preserved by construction rather than by the model's goodwill. `spliceParagraphs` writes them back by byte offset, leaving every other character identical.

Location is **all-or-nothing**: if a single targeted issue quotes nothing findable, the whole chapter falls back to `FIXCH`, because fixing two of three issues by span and silently dropping the third would misreport what happened. The same fallback catches a model that returns the wrong set of paragraph keys, an empty paragraph, or a paragraph containing a blank line (which would split into two at splice time and shift every later index). `fix-report.json` records `mode`, `paragraphsTouched`, `spanFallback` and `untouched` — the fraction of paragraphs byte-identical afterwards, which is the blast radius measured without an LLM. Observed on a real run: 58 of 60 paragraphs untouched (0.967).

Span mode forced a second correction that is easy to miss. **A scoped edit needs a scoped measurement.** The prose gate originally compared the whole chapter before and after, which in span mode means judging a two-paragraph change through 58 unchanged ones — the slack alone (`floor(100/25)` ≈ 4 fragments) swallows the entire signal. `ChapterRewrite` therefore carries `scopedBefore`/`scopedAfter`, exactly the text that changed, and the gate measures those; in whole-chapter mode they are the whole chapter, so the caller never branches. The difference is not theoretical: the first run after scoping the measurement immediately rejected a rewrite for "1 câu dưới 10 chữ (trước có 0)" on 185 measured words, a regression the diluted version would have absorbed silently.

One consequence is **not** solved and should be treated with suspicion: `REVIEW_CH`'s score is noisy at this scale. A span fix that changed 2 of 60 paragraphs scored 51 → 45, six points across six criteria on a 96.7%-identical chapter — almost certainly judge noise rather than damage. The 85% score-collapse guard was written for whole-chapter rewrites, where the signal is large; against a scoped edit it is mostly measuring its own variance, and it survived that run by a margin (88%) rather than by judgement. Do not re-tune it on one data point, but do not read a score swing on a span fix as evidence of anything either. `final_story.txt` is rebuilt only if at least one fix was kept. `fix-report.json` records `{chapter, kept, note, mode, paragraphsTouched, spanFallback, untouched, proseBefore, proseAfter, proseRegressions, proseGains, issuesTargeted, issuesFixed, newProblems, scoresBefore, scoresAfter}` per chapter, so a reverted fix still says why — and a `scoresAfter` of `null` beside a prose rejection is the visible sign that the two verification calls were skipped rather than failed. `POST /api/fix/:name` also takes `{maxRounds}` (1-10, default 1), surfaced as the **Số vòng sửa tối đa** field. Above 1, `fixStory` loops: after each round the chapters it kept already carry fresh `REVIEW_CH` scores *and a fresh issue list* from the verify step, so those are written straight back into `review-report.json` and become the next round's input — no separate review pass, no extra call. Round 1 hands `FIXCH` every issue the chapter has (or just the hand-picked ones); later rounds hand it only the `cao`/`vừa` ones, falling back to the full list if none are left, and skip a chapter with no issues at all. The loop stops at whichever comes first: no chapter left that `needsFix` picks, the round cap, or a round where no rewrite was kept (the model has stopped making progress and further rounds only cost calls) — but a round that kept nothing *because the calls failed* raises instead of stopping quietly, see below.

Both stages abort with a `HET_KHA_NANG:`-prefixed error the moment a call fails with something that looks like exhausted capacity (`429`/`529`/`503`, rate limit, overloaded, quota, "session limit"). This exists because the two failure modes are opposite and used to be indistinguishable: a 10-round fix run once hit the Claude session limit at chapter 7, ground through 18 chapters × 3 retries, kept nothing in round 2, and the "no progress" guard read that as "the model has nothing left to fix" — so the job reported `complete` on a story where 18 of 24 rewrites never ran. The prefix is stripped in `src/server.ts` before the message reaches the UI, which shows it as a failed job. When more than one round ran, `REVIEW_SUM` is re-run once at the end so the overall score and `topIssues` describe the story that now exists. `fix-report.json` records the `round` on every entry plus the total `rounds`.

The report is written *before* `final_story.txt` is rebuilt: the rebuild is the step most likely to fail (a half-written story has no file for every outline chapter, which is why it is now skipped rather than throwing), and losing the report of a rewrite that already happened on disk is worse than skipping the rebuild. Note `pre-fix/` is a subdirectory rather than `chapter-<n>.orig.txt` because `src/tts/index.ts`'s fallback globs `chapter-*.txt` and would otherwise splice the stale copies into the audio.

Prompts (`src/prompts/`, one spine per genre — see **Genre and setting** above) are Vietnamese and instruct the model to output either strict JSON (no Markdown) or plain narration text (no Markdown, no meta-commentary like "Dưới đây là..."). `cleanGeneratedStory` (`src/utils.ts`) strips Markdown artifacts and stock LLM preambles from narrative output as a second line of defense.

### Retry/validation model (`src/ollama.ts`)

Two retry wrappers around `askLLM`, both doing 3 attempts. `askJSON` steps temperature down each retry (`t` → `0.2` → `0.1`) to trade creativity for format compliance, since its failure mode is malformed JSON. `retryLLM` deliberately does **not** — it retries at the configured temperature, because its failure modes (network/API errors, empty response, `max_tokens` truncation) are not caused by temperature, and collapsing a long-form narrative generation toward greedy decoding invites degenerate repetition, making the retry likelier to fail than the first attempt. Both sleep between attempts (`backoffMs`): exponential with jitter from an 800 ms base, or a 5 s base when the error text looks like throttling (`429`/`529`/`503`/"rate limit"/"overloaded") — without this, parallel jobs burn all 3 attempts within a second of a single rate-limit response.

- `askJSON` — expects JSON, uses `extractJSON` to strip code fences / find the outermost `{}`/`[]` if the model wraps the JSON in prose, then runs an optional `validate(x)` callback that throws on missing/malformed fields.
- `retryLLM` — expects non-empty raw text (used for scene writing and chapter editing).

Per the README: Story Bible, Outline, Hook, Chapter Plan, Scene Writing, Chapter Editing and Outro are all critical — if they still fail after 3 attempts, the whole run aborts (no partial/corrupt story is written). Memory updates and the continuity check are the non-critical stages that retry but don't abort the run on failure.

### TTS pipeline (`src/tts/index.ts` + `src/tts/worker.py`)

Runs after a story exists, either manually via the CLI or driven by the web server:

1. The exported `runTTS(storyDir, opts, onProgress?)` reads `final_story.txt` (or falls back to concatenating `chapter-*.txt`), cleans Markdown, splits into ≤450-char segments on paragraph/sentence boundaries, and writes `tts/manifest.json` (segments with id/text/output path).
2. It spawns `python src/tts/worker.py --manifest ... --voice ... --ref-audio ...`, which loads `vieneu.Vieneu`, does reference-audio voice cloning per segment, and writes `tts/audio/<0001>.wav` etc. Existing output files >1000 bytes are skipped, so reruns resume like the story pipeline.
3. Default voice sample path is `voices/minhthu.mp3`; override with `TTS_REF_AUDIO`. `TTS_REF_TEXT` (transcript of the sample) improves cloning quality when set.
4. `opts.pipeOutput` controls stdio: unset/falsy (the CLI path, `main()` at the bottom of the file) uses `stdio: "inherit"` so the Python process's TTY/prompts pass through untouched; `pipeOutput: true` (used by `src/server.ts`) pipes stdout/stderr instead, parsing `[i/total] SKIP|TTS ...` lines out of stdout into `TtsProgressEvent`s (`src/types.ts`) for `onProgress`.

### Web server (`src/server.ts`)

Express app (`npm start`, default port 4000, binds `127.0.0.1` only) serving `public/` statically and `output/` at `/output` for direct file access (story text, audio).

**Generate jobs run many-at-a-time.** In-memory state is a `Map<name, GenerateJob>` (`generateJobs`) plus a FIFO `jobQueue`; `pump()` promotes queued jobs to running while `runningCount() < maxParallelStories`, and is re-run whenever a job finishes, a job is stopped, a batch is submitted, or the limit changes via `POST /api/settings`. Job identity is the story name, so each job writes to its own `output/<name>/` and they never collide; re-submitting a name that is already `queued`/`running` 409s. `POST /api/generate` accepts either one story (`{name, idea|ideaFile, ...}`) or a batch (`{items: [...], ...shared config}`) and returns the queued names plus per-item `failed` entries — a bad item never blocks the rest. `POST /api/generate/stop` takes `{name}` (a queued job is dropped from the queue and marked `stopped` immediately; a running one gets `abortRequested`) or `{all: true}`. Per-story SSE stays at `GET /api/generate/stream?name=`, replaying buffered events on (re)connect and now including scheduler events `queued`/`started`; `GET /api/jobs` and `GET /api/jobs/stream` expose a whole-queue snapshot (`JobSummary[]`, `running`, `maxParallelStories`) that drives the home screen's queue panel.

Parallelism is deliberately **across** stories, not within one — scenes depend on the previous scene's `RECENT` text and chapters on the running memory, so intra-story concurrency would break continuity. Because each job's LLM calls are strictly sequential, concurrent LLM requests equal running jobs, which is why one knob (`maxParallelStories`) is enough.

TTS is still single-job-at-a-time (`ttsJob`): `POST /api/tts/:name` 409s if one is running, since the Python worker is GPU/CPU-bound and parallelising it would not help. All routes that resolve a filesystem path from request input go through a shared `resolveUnder(root, name)` helper to keep the path inside `output/`/`stories/`.

### Config (`src/config.ts`, `src/types.ts`)

All tunables live in one `Config` object, overridable via env vars: `OLLAMA_MODEL`, `OLLAMA_URL`, `OLLAMA_NUM_CTX`, `PYTHON_COMMAND`, `TTS_VOICE`, `DEEPSEEK_API_KEY`, `DEEPSEEK_MODEL`, `MAX_PARALLEL_STORIES`, `STORY_GENRE`, `STORY_SETTING` (`src/tts/index.ts` imports `config` for the TTS ones; it separately reads `TTS_REF_AUDIO`/`TTS_REF_TEXT` from env since those aren't in `Config`). Story length is controlled by `durationMinutes × targetWordsPerMinute`, chapter/scene count by `chapters`/`scenesPerChapter`.

`Config.genre` (`"drama"` default, `STORY_GENRE`) and `Config.setting` (`"auto"` default, `STORY_SETTING`) are the two axes described under **Genre and setting** above. `settings.json` may carry `genre` and `setting` too, which makes them the default selection of the web UI's create-story form and of a CLI run. Two places have to cooperate for that to hold: `GET /api/config` merges `loadSettingsOverrides()` over `config` before answering (the form preselects its dropdowns from that response), and `POST /api/settings` copies any existing `genre`/`setting` through when it rewrites the file — the Settings screen has no field for them, and without that copy every save would silently delete them. An invalid value in `settings.json` is dropped rather than applied (`asGenre`/`asSetting` in `src/config.ts` return `null` and the override is skipped), so a typo there falls back to the built-in default instead of failing a run. Whatever is chosen only matters until the bible is written — from then on `story_bible.json`'s `genreId`/`settingId` are what every later stage reads.

`Config.numCtx` (Ollama only, default 32768) is **one budget shared by prompt and generation**, not a prompt-only limit — Ollama stops with `done_reason:"length"` the moment `prompt_eval_count + eval_count` reaches it, which surfaces downstream as a truncated reply: `Invalid JSON` from `extractJSON` on the JSON stages, or a half-written chapter on the narrative ones. The old 4096 default sat right at the Outline stage's real cost (measured: 1647 prompt + ~2200 generation tokens), so runs failed intermittently depending on how verbose the model happened to be, and all 3 retries failed together because temperature does not change how much output the task needs. Lower it via `OLLAMA_NUM_CTX` only if the GPU cannot hold the KV cache (9B at 32768 ≈ 6.2 GB VRAM).

`Config.maxParallelStories` (default 3, clamped to 1–16 when set from `settings.json`) caps how many generate jobs the web server runs at once; it is a server-only knob (the CLI runs one story per process). Set it to 1 for Ollama, higher for DeepSeek/Claude.

`Config.editorModel` (default empty, `EDITOR_MODEL` or the Settings dropdown) swaps the model used by stages 8 and 9 only — `generateStory` derives an `ec` config from `c` with the model fields replaced, and every review/fix call takes `ec` while everything that writes the story takes `c`. Provider is deliberately not overridable: the point is "write with the cheap model, judge with the strong one", and a model grading its own prose is the failure this exists to avoid (a run where Haiku wrote chapters 6-12 was only caught because the review happened to run under a stronger model). It is recorded in `run-info.json` when set.

`Config.autoReview` / `Config.autoFix` (both default off; `AUTO_REVIEW=1`/`AUTO_FIX=1` or the Settings checkboxes turn them on) gate stages 8 and 9 at the end of `generateStory`. They default off because both stages cost N+1 and 2-per-chapter extra LLM calls and the fix stage overwrites chapter files, so the normal flow is: write the story, read the report, then decide.

Stages 8 and 9 are also reachable on demand via `POST /api/review/:name` and `POST /api/fix/:name`, driven by the **Chấm điểm** / **Sửa N chương có lỗi** buttons on a story's screen. Those routes call `reviewStory`/`fixStory` with `force=true` — a button press must actually re-run, so the file-existence cache only serves the automatic path. They are queued as ordinary jobs (`GenerateJob.kind` is `"generate" | "review" | "fix"`), which is why the queue panel, SSE stream, stop button and `maxParallelStories` cap all work on them without a second job mechanism. `/api/fix/:name` 400s when there is no `review-report.json` yet, and `reviewStory` scores only the chapters that exist on disk so the button is safe to press on a half-written story.



**The hook is editable after the story is written.** The story screen shows `hook.txt` in a textarea with **Lưu lời dẫn** and **Viết lại cho dễ nghe hơn**. `PUT /api/hook/:name` saves hand-typed text and calls no model (an 80-character floor is the only guard); `POST /api/hook/:name` runs `rewriteHook` and takes the same `{provider, model}` override as review/fix, resolved by the shared `taskConfig` helper. `rewriteHook` is a **measured loop, not a single call**: it writes a candidate, measures it with `src/quality.ts`, and keeps it only if nothing measurable got worse. A rejected candidate does not just get retried — the numbers that failed are fed back into the prompt through `{{FEEDBACK}}`, so the next attempt is told exactly what broke ("có 2 câu dưới 10 chữ, gộp chúng bằng từ nối"). It stops at the first candidate that passes, so the normal case still costs one call; three failures in a row means the original hook is kept untouched and the response says why. The button promises higher quality, not different words. Neither is queued as a job: the queue exists to throttle work costing dozens of calls, and a third `GenerateJob.kind` plus an SSE stream for a wait under a minute costs more than it buys. Both write the previous text to `pre-fix/hook.txt` — one step back, the same convention the fix pass uses for chapters — and both rebuild `final_story.txt` through the shared `rebuildFinalStory`, because changing `hook.txt` without rebuilding leaves the file the user reads and the file TTS reads still carrying the old hook. `rebuildFinalStory` skips the write when fewer chapters exist than the outline names, so either button is safe on a half-written story; the response reports `chaptersFound`/`total` and the screen says which happened. Existing audio is **not** deleted — the panel warns that `tts/audio/` still speaks the old hook and leaves the call to the user.

The plain-language rules in `core.ts` are two halves that pull against each other, and only one of them is obvious. "Easy to understand" on its own produces staccato: the first draft told the model *"câu nào dài hơn thì cắt đôi"* and it returned three subjectless fragments in a row — every word easy, the whole thing reading like a bulleted list rather than someone telling a story. So the block is headed **NÓI CHO DỄ HIỂU MÀ VẪN MƯỢT** and the sentence rule is *rewrite it shorter*, never *cut it in half*: every sentence must stand alone with a subject, lengths must alternate (a medium sentence to narrate, a short one to land), and clauses join with everyday connectives (`rồi`, `mà`, `nhưng`, `vì`, `thế là`) instead of another full stop. `check-genre-prompts.ts` asserts the anti-chopping clause survives, because deleting it is invisible — the prompt still reads sensible and the output still scores as "clear". Smoothness costs words, so it pulls against the length ceiling: the romance example hook sits at 80 words and rewrites to 81 against a ceiling of 80. That is why `compareProse` treats the ceiling as *relative with slack* — a rewrite is only blamed for an overrun it actually caused, and only past `LENGTH_SLACK` (5 words). Blocking on the absolute ceiling would reject the best rewrite over a single word and then order the loop to cut words, which is the fastest possible route back to fragments. (An earlier draft of this file said 82 words; that count included the em-dash `—` as a word. `measureProse` is the authority on what a word is.)

`HOOKFIX` deliberately carries no `{{SET_*}}` variable. It rewrites a hook that already exists, so it never needs to know the setting — and the one clause that ever came close to deleting a Chinese-set story's cast was a "strip foreign words" instruction inside a fix prompt. `check-genre-prompts.ts` asserts the only variables in `HOOKFIX` are the three `rewriteHook` fills (`{{HOOK}}`, `{{BIBLE}}`, `{{WORDS}}`), so a fourth one fails the build rather than shipping `{{...}}` to the model as literal text. Its length instruction is the ceiling, never the old hook's length: an early draft said both "keep roughly the old length" and "never exceed `hookWords` + 15%", which contradict each other whenever the existing hook is already over — as romance's example hook, at 82 words against a ceiling of 80, is.

Both routes accept an optional `{provider, model}` body so a single review or fix run can go to a different backend than the one in `settings.json` — cross-checking a DeepSeek-written story with Claude, or re-scoring with a stronger model just this once. The override applies to that job only and never writes `settings.json`. An explicit choice clears `editorModel` for that run, because `editorModel` is a bare model name that belongs to the configured provider and would be meaningless once the provider changes. `review-report.json` and `fix-report.json` therefore record `provider`/`model`: with the judge now selectable per run, a score is not interpretable without knowing who gave it.

`POST /api/fix/:name` also accepts `{selection: {"<chapter>": [issueIndex, ...]}}`, produced by ticking individual issues on the review screen. With a selection present `fixStory` ignores the `needsFix` filter and rewrites exactly the listed chapters, handing `FIXCH` only the ticked issues — so a chapter can be fixed for one specific complaint without the model rewriting around the other five. `fix-report.json` records `issuesTargeted` per chapter. Everything else (the `pre-fix/` backup, the 85% length floor, the re-score-and-revert guard) applies unchanged.

`/api/stories` and `/api/stories/:name` report `staleChapters`: chapters whose `chapter-<n>.txt` mtime is newer than the score that applies to them **by more than `MTIME_TOLERANCE_MS` (2000 ms)**, i.e. rewritten since they were last judged. The tolerance is not slack, it is exFAT: there the mtime resolution is two seconds and rounds *up*, so a chapter written at 12:25:19.2 reads back as 12:25:20.000 — newer than the report written right after it — and the last chapter of every fix run was flagged "cũ" and its owner invited to pay for a re-score. Nothing legitimate rewrites a chapter within two seconds of its own report; one LLM rewrite takes minutes. The reference time is `review-report.generatedAt`, except for a chapter the fix stage rewrote *and kept* — that text was re-scored inside the fix stage, so its reference is `fix-report.generatedAt` and it must not be flagged. The UI marks those rows "cũ" and warns on the story screen and the home table, because a score displayed next to text it was not computed from is worse than no score at all.

`Config.provider` (`"ollama"|"deepseek"`) selects which LLM backend `src/ollama.ts`'s `askLLM` calls — Ollama's `/api/chat` or DeepSeek's OpenAI-compatible `/chat/completions`, both behind the same `askJSON`/`retryLLM` retry wrappers, so nothing downstream of `askLLM` needs to know which provider is active. `loadSettingsOverrides()` (`src/config.ts`) reads an optional `settings.json` (git-ignored, repo root) and returns override fields; both the CLI (`src/index.ts`) and the web server (`src/server.ts`, `POST /api/generate`) merge it over the base `config` before each run, so switching provider via the web UI's Settings screen (`GET`/`POST /api/settings`) takes effect for the CLI too without restarting anything. Absent `settings.json` behaves exactly as before (`provider:"ollama"`). Once a user saves the Settings screen, `settings.json` becomes the source of truth for `model`/`provider`/`deepseek` and outranks the env-var defaults (e.g. `OLLAMA_MODEL`) from that point on.

## Code style note

Source files under `src/` (excluding `src/tts/index.ts`) are written densely — no whitespace between statements, minimal formatting. This appears to be the existing convention for the core pipeline files; match it when editing those files rather than reformatting.
